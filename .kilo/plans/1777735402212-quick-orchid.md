# Plan: Check if Codebase Follows FSD (Feature-Sliced Design)

## Objective
Determine whether the current codebase adheres to Feature-Sliced Design (FSD) principles.

## Findings

### 1. Current Directory Structure
The `src` directory contains:
- `assets/` - Static assets
- `components/` - UI components (including `ui/` subdirectory)
- `contexts/` - React context providers
- `data/` - Data files (storeOwnerData.ts, products.ts, etc.)
- `hooks/` - Custom React hooks
- `lib/` - Utility functions
- `pages/` - Page components organized by user role
- `test/` - Test files
- Configuration and entry files (App.tsx, main.tsx, etc.)

### 2. FSD Layer Mapping Analysis
The current structure does NOT follow FSD conventions:
- No `src/shared`, `src/entities`, `src/features`, `src/widgets`, `src/processes`, or `src/app` directories
- Pages are organized by user role (`StoreOwner*`, `Marketer*`, etc.) rather than by feature
- Components are in a flat structure with UI primitives in `components/ui/`
- Business logic appears to be distributed across contexts, hooks, and data files
- No clear separation between layers as defined by FSD

### 3. Current Organizational Patterns
- **Pages**: Organized by user role (StoreOwner, Marketer, Delivery, BackOffice, Admin)
- **Components**: Mixed UI components and domain-specific components in `components/`
- **Contexts**: React context providers for theme, orders, locale, cart, auth
- **Data**: TypeScript files with mock data or constants
- **Hooks**: Custom hooks for pagination, interests, toast, mobile detection
- **Lib**: Utility functions

### 4. Configuration Check
- ESLint configuration does not include FSD-specific rules
- No FSD-related documentation found (no README.md in project root)

## Conclusion
The codebase does **NOT** follow Feature-Sliced Design (FSD) principles. The current organization follows a role-based or feature-grouped structure rather than FSD's layer-based approach.

## Recommendations for FSD Migration
If adopting FSD is desired:
1. Create FSD layer directories: `shared`, `entities`, `features`, `widgets`, `pages`, `processes`, `app`
2. Migrate existing code:
   - Move reusable utilities, UI components, and types to `shared/`
   - Identify business objects (User, Product, Order) for `entities/`
   - Extract user interactions and business logic to `features/`
   - Create composite units in `widgets/`
   - Keep route components in `pages/`
   - Move app-wide providers to `app/`
3. Update imports to respect FSD layer dependencies (higher layers can import from lower layers, but not vice versa)
4. Consider adding ESLint rules to enforce FSD boundaries

However, given the project's current role-based organization (which works well for its multi-portal structure), migrating to FSD may not provide significant benefits unless the project plans to scale significantly in complexity.
